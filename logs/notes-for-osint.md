## Standing constraints

These never clear. They are properties of OSINT that CORPUS depends on, recorded so that changing one is a decision rather than an accident. *(These replace the pre-migration constraints, which were about OSINT's `outputs/` — CORPUS no longer reads that; it authors its own.)*

**`raw/`, `lookups/` and `wiki/` must stay git-tracked and committed.** `raw/` and `wiki/` are the evidence CORPUS compiles and reports from; `lookups/` gives the vocabularies. Gitignoring or failing to commit any of them loses the one state that is not recoverable — the working tree is what the mirror backs up and what a rebuild restores from, and an OSINT tree that never commits leaves every change since the last one at risk together. *(Corrected 2026-08-14: this said CORPUS reads OSINT's committed `HEAD` for all three. It does not — every current reader goes through the workroot junctions into OSINT's **working tree**, exactly as it does for `index/`. The only script that reads `HEAD` is `pull.py`, and what it reads is OSINT's `outputs/`, which the migration retired. The requirement stands; the reason given for it did not.)*

**`index/` is not a constraint at all: CORPUS does not read OSINT's.** *(Bill, 2026-08-14 — "I don't like this OSINT dependency… what is the need for index".)* An index is a cache of a tree CORPUS can already read in full, so nothing about it needed to be OSINT's copy of the file. CORPUS now builds its own from `raw/` and `wiki/`, into its gitignored workroot, in about 5 seconds, rebuilt automatically whenever either tree moves. OSINT's `index/` stays untracked and stays OSINT's business; whether it is fresh, whether `vault.db` earns its keep, whether a rebuild skips the DB — none of it reaches CORPUS any more. `vault_lib._assert_own_index()` remains as a backstop and can no longer fire in normal use, because the index it would refuse to rebuild is now physically inside the tree doing the rebuilding. *(This paragraph previously asked OSINT to keep its index fresh **for** CORPUS. It no longer does, and that is one fewer thing that can stop a build.)*

**A slug is a permanent public identifier and must never be reissued.** Once the site is live a slug is the target of a provenance link inside a PDF a journalist or academic has already downloaded, and that link has to resolve years later. Retiring a slug is survivable — the URL can say the record was withdrawn, and when. **Reusing one for a different record is not**: it silently redirects an old citation to unrelated evidence. A replaced or corrected source takes a new slug.

**A record that leaves `raw/` takes a published citation with it.** CORPUS resolves every citation's slug to a URL through an index it rebuilds from `raw/` itself, so a deleted record now simply stops resolving — the *mechanism* is no longer at risk, and no index hygiene is owed to CORPUS. What is still owed is the decision above it: once the site is live, deleting a `raw/` record retires a slug that a published PDF may already cite, so a deletion is a publishing decision and not only a vault one. See note 4. *(Rewritten 2026-08-14: this constraint used to say `index/` must reflect `raw/` including deletions, which was CORPUS asking OSINT to maintain a cache CORPUS now owns.)*

## Unresolved

**1** (2026-08-06) — **Repo size.** ~4.6 GB and growing against GitHub's soft 5 GB ceiling; the tracked PDFs in `raw/` are the weight. Not site work, but the site cannot launch over it, and it makes granting vault access on request a chore rather than an offer. The reasoning that removed the budget-archive PDFs applies to them.

**2** (2026-08-06) — **`wiki/capture-rule.md` lines 12–14 say "never republished".** Substantively still true — the claim is about the verbatim bodies in `raw/`, which stay private, and that is what the CDPA s.29 basis rests on. But once the public site exists, a reader who does not know the body/metadata distinction will read it as contradicting the rule. Reword to say the *bodies* are never republished, so the sentence survives the site. Wording, not substance; low priority.

**3** (2026-08-11) — **Two finance-record fields are undocumented.** `amount_basis` and `amount_quality` are carried on the finance records in `raw/` but are not defined in `wiki/finance-record-spec.md`. CORPUS publishes a field dictionary for the non-state-finance download, and those two currently have to be read off the data rather than cited to a spec. A one-line definition of each in the record spec closes it. *(The CSV export itself is now CORPUS's; this is about the underlying record fields, which are OSINT's.)*

**4** (2026-08-13) — **`index/` is append-only, so a deleted source leaves a live slug — and is the DB still the right tool?** `2026-08-07-nitda-partners-women-educators-on-nationwide-digital-literacy-drive` (Tech Africa News, NGA) was in the catalogue CORPUS built on 2026-08-11 and gone on 2026-08-13; no file remains under `raw/`, but the slug is still in `index/vault.db`. Bill's read: OSINT deleted the `raw/` record with permission, and the index only appends, so the slug was never removed. Two things follow. **(a)** A permissioned `raw/` deletion must also clear the slug from `index/` (or `index/` must be rebuilt, not appended), or the standing constraint above is broken — once live, a record that vanishes between two builds is a citation that can break. **(b)** Worth questioning whether `index/vault.db` earns its keep at all now: CORPUS reads `index/` only to resolve slug→URL; if that need is better met by a rebuilt-each-time file than by an append-only database, the DB may be scaffolding the migration has outgrown. A decision, not just a cleanup. *(Was note 10.)*

*(**The premise needs correcting, 2026-08-14.** `index/` is not append-only: OSINT's own `.gitignore` describes it as "rebuilt from scratch and never appended to, so it cannot drift out of step with the vault — only go stale". The dangling slug is therefore staleness, not an append. What makes that more than a technicality is **which** part was stale. `build_index()` takes `db=False` by default, so a routine rebuild writes `files.jsonl` and `links.jsonl` and leaves `vault.db` alone — and on disk today the two `.jsonl` files are dated 2026-08-13 while `vault.db` is dated 2026-08-10. The DB goes stale independently of the rest of the index, and nothing about a read of it says so. That sharpens **(b)** rather than answering it: the question is not only whether the DB earns its keep, but whether an artefact that the ordinary rebuild silently skips can be a citation-resolution path at all.)*

*(**And one step further, 2026-08-14.** CORPUS never opens `vault.db` at all. `build_db()` is the only reference to it in `scripts/`, and it writes; slug resolution runs `load_index()` → `files.jsonl`, which is rebuilt from scratch every time. So a deleted `raw/` record drops out of CORPUS's read path at the next rebuild and **cannot reach a CORPUS citation**. What the dangling slug endangers is a link already published in a PDF someone has downloaded — which makes **(a)** a question about `raw/` deletion policy rather than about the index, and makes **(b)** stronger again: the DB is on nobody's read path here.)*

*(**And CORPUS is now out of it entirely, 2026-08-14.** CORPUS builds its own index from `raw/` and `wiki/` and never opens OSINT's. Both halves of this note are OSINT's own call to make on OSINT's own terms — **(a)** is a slug-permanence question the standing constraints already carry, and **(b)** is about a DB only OSINT queries.)*

**5** (2026-08-14) — **Proposal: `INGEST` could establish the earlier position a progress report compares against.** *(Bill's suggestion; recorded here for an OSINT session to weigh, not actioned. Was note 11.)* CORPUS's report ledger carries `position_start` and `position_end` per row — the substance of a position at each end of a twelve-month window, as free text: `30 branches, five banks (2025-08)` against `296 branches, four banks`. `position_end` comes from the record in hand. **`position_start` does not**: establishing it means going back through the wiki for an earlier relevant occurrence of the same object, which is a different kind of search from the one BUILD is doing, and it happens **once per row** — once a row is in the ledger the start position never changes.

That work sits closer to `INGEST` than to CORPUS. INGEST is already reading each new record against the base and is already across places, concepts and intersections, which is exactly the traverse `position_start` needs; CORPUS reaches `raw/` and `index/` read-only and has no equivalent view. Doing it at ingest would also do it at the one moment the question is cheap — while the record is being placed — rather than at report time on a base someone has to re-enter.

Current state, for whatever it is worth to the decision: `position_start` is filled on 4,112 of 5,421 rows (75%), `position_end` on 4,760 (87%). A row with no `position_start` renders ***Baseline not held***, so a quarter of rows currently publish as having no stated baseline. Bill's own view is that the field is ambitious and he is **not confident it is currently accurate** — so this is worth settling on correctness grounds, not only on where the work belongs. Nothing in CORPUS blocks on it; the field degrades gracefully.

**6** (2026-08-14) — **The UNITEL outage has two incompatible durations in the base.** `2026-07-30-...unitel-restores-services...` documents restoration in stages — localised from 11:45 on 29 July, full 2G/3G national coverage about 23:00 on 30 July, messaging and electronic airtime back on 31 July, i.e. three to four days. `2026-08-10-angola-unitel-cyberattack-customer-reaction` frames the same event as running 28 July to 5 August, nine days, for about 20.8 million customers. **7** (2026-08-14) — **`budget-archive/COM/` holds budget documents that nothing downstream can cite: the `-companion` records for them do not exist.** Four rows on Comoros's ledger cite `…-companion` slugs — `2025-03-14-com-rapport-execution-budgetaire-exercice-2024-companion`, `2025-09-04-com-lettre-de-cadrage-budgetaire-2026-companion`, `2024-09-04-com-lettre-de-cadrage-budgetaire-2025-companion`, `2026-03-01-com-contrat-materiels-informatiques-crde-ama-sarl-companion`, `2025-11-03-com-liste-des-marches-et-beneficiaires-effectifs-companion` — and no file of that name exists anywhere in OSINT. So the companion markdown records that would carry a `url:` and make them citable were either never written or removed. Two consequences: the rows publish an *Implemented* position a reader cannot follow, and CORPUS cannot fix it — not for want of access, since CORPUS may read anything in OSINT *(Bill, 2026-08-14)* and `budget-archive/` is a junction away, but because a PDF in an archive is not a citable record. What is missing is the companion markdown carrying a `url:`, and minting that is a write into OSINT, which CORPUS does not do. CORPUS has left the four rows citing the missing slugs rather than quietly restating them, so `report-render.py --check` keeps reporting them. This is the §8 uncitable-artefact class, found by check M. Budget work is suspended, so it may be deliberate that these are dormant. *(Raised by BUILD, 2026-08-14. Was note 13.)*

**8** (2026-08-14) — **OSINT's `index/` was built from CORPUS's workroot and holds `raw/` only. It needs one rebuild in an OSINT session, and CORPUS's build is stopped until it gets one.** `index/meta.json` records **10,178** files over roots that include `wiki/`, `sweep/` and `budget-archive/`; a walk of those roots in OSINT counts **13,580**. A build run in OSINT could not have produced 10,178 — that is `raw/` alone, which was all that resolved in CORPUS's workroot — so the index on OSINT's disk was written by a CORPUS run on 2026-08-13, the timestamp `files.jsonl` and `links.jsonl` still carry. It is missing all 2,410 `wiki/` files, 632 `budget-archive/`, 310 `sweep/`, 23 `new-budget/`, 12 `reviews/`, 9 `queries/` and 6 `new/`. This is the write across the boundary that `vault_lib._assert_own_index()` was added on 2026-08-14 to make impossible: it landed the day before the guard existed, and a guard cannot undo what preceded it. **Anything in OSINT that asks the index about the wiki is reading a hole.** CORPUS's own reads were never wrong — `slug_urls()` takes only `folder == "raw"` rows, and for those the index is complete — but CORPUS now *stops* rather than reads: its workroot exposes all eight roots as of today, so it walks 13,580 against a meta of 10,178, finds the index stale, and raises `ForeignIndex` rather than rebuild a tree that is not its own. The repair is `python scripts/build-index.py` in an OSINT session, about 77 seconds. *(Found by CC reviewing the workroot change, 2026-08-14.)*

*(**No longer urgent, same day.** This note was written while CORPUS still read OSINT's index and was stopped by it. CORPUS now builds its own, so nothing here waits on the rebuild and nothing in CORPUS is wrong in the meantime. The note stands because the index on OSINT's disk is still a partial one that OSINT's own lint and queries will read as complete, but it is OSINT's hygiene now, at OSINT's convenience.)*
