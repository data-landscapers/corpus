## Standing constraints

These never clear. They are properties of OSINT that CORPUS depends on, recorded so that changing one is a decision rather than an accident. *(These replace the pre-migration constraints, which were about OSINT's `outputs/` — CORPUS no longer reads that; it authors its own.)*

**`raw/`, `lookups/` and `wiki/` must stay git-tracked and committed.** `raw/` and `wiki/` are the evidence CORPUS compiles and reports from; `lookups/` gives the vocabularies. Gitignoring or failing to commit any of them loses the one state that is not recoverable — the working tree is what the mirror backs up and what a rebuild restores from, and an OSINT tree that never commits leaves every change since the last one at risk together. *(Corrected 2026-08-14: this said CORPUS reads OSINT's committed `HEAD` for all three. It does not — every current reader goes through the workroot junctions into OSINT's **working tree**, exactly as it does for `index/`. The only script that reads `HEAD` is `pull.py`, and what it reads is OSINT's `outputs/`, which the migration retired. **`pull.py` was itself deleted on 2026-08-16**, so no CORPUS script reads OSINT's `HEAD` at all now — every read goes through the workroot junctions into the working tree. The requirement stands; the reason given for it did not.)*

**`index/` is not a constraint at all: CORPUS does not read OSINT's.** *(Bill, 2026-08-14 — "I don't like this OSINT dependency… what is the need for index".)* An index is a cache of a tree CORPUS can already read in full, so nothing about it needed to be OSINT's copy of the file. CORPUS now builds its own from `raw/` and `wiki/`, into its gitignored workroot, in about 5 seconds, rebuilt automatically whenever either tree moves. OSINT's `index/` stays untracked and stays OSINT's business; whether it is fresh, whether `vault.db` earns its keep, whether a rebuild skips the DB — none of it reaches CORPUS any more. `vault_lib._assert_own_index()` remains as a backstop and can no longer fire in normal use, because the index it would refuse to rebuild is now physically inside the tree doing the rebuilding. *(This paragraph previously asked OSINT to keep its index fresh **for** CORPUS. It no longer does, and that is one fewer thing that can stop a build.)*

**A slug is a permanent public identifier and must never be reissued.** Once the site is live a slug is the target of a provenance link inside a PDF a journalist or academic has already downloaded, and that link has to resolve years later. Retiring a slug is survivable — the URL can say the record was withdrawn, and when. **Reusing one for a different record is not**: it silently redirects an old citation to unrelated evidence. A replaced or corrected source takes a new slug.

**A record that leaves `raw/` takes a published citation with it.** CORPUS resolves every citation's slug to a URL through an index it rebuilds from `raw/` itself, so a deleted record now simply stops resolving — the *mechanism* is no longer at risk, and no index hygiene is owed to CORPUS. What is still owed is the decision above it: once the site is live, deleting a `raw/` record retires a slug that a published PDF may already cite, so a deletion is a publishing decision and not only a vault one. See note 4. *(Rewritten 2026-08-14: this constraint used to say `index/` must reflect `raw/` including deletions, which was CORPUS asking OSINT to maintain a cache CORPUS now owns.)*

**4** (2026-08-13) — **`index/` is append-only, so a deleted source leaves a live slug — and is the DB still the right tool?** `2026-08-07-nitda-partners-women-educators-on-nationwide-digital-literacy-drive` (Tech Africa News, NGA) was in the catalogue CORPUS built on 2026-08-11 and gone on 2026-08-13; no file remains under `raw/`, but the slug is still in `index/vault.db`. Bill's read: OSINT deleted the `raw/` record with permission, and the index only appends, so the slug was never removed. Two things follow. **(a)** A permissioned `raw/` deletion must also clear the slug from `index/` (or `index/` must be rebuilt, not appended), or the standing constraint above is broken — once live, a record that vanishes between two builds is a citation that can break. **(b)** Worth questioning whether `index/vault.db` earns its keep at all now: CORPUS reads `index/` only to resolve slug→URL; if that need is better met by a rebuilt-each-time file than by an append-only database, the DB may be scaffolding the migration has outgrown. A decision, not just a cleanup. *(Was note 10.)*

*(**The premise needs correcting, 2026-08-14.** `index/` is not append-only: OSINT's own `.gitignore` describes it as "rebuilt from scratch and never appended to, so it cannot drift out of step with the vault — only go stale". The dangling slug is therefore staleness, not an append. What makes that more than a technicality is **which** part was stale. `build_index()` takes `db=False` by default, so a routine rebuild writes `files.jsonl` and `links.jsonl` and leaves `vault.db` alone — and on disk today the two `.jsonl` files are dated 2026-08-13 while `vault.db` is dated 2026-08-10. The DB goes stale independently of the rest of the index, and nothing about a read of it says so. That sharpens **(b)** rather than answering it: the question is not only whether the DB earns its keep, but whether an artefact that the ordinary rebuild silently skips can be a citation-resolution path at all.)*

*(**And one step further, 2026-08-14.** CORPUS never opens `vault.db` at all. `build_db()` is the only reference to it in `scripts/`, and it writes; slug resolution runs `load_index()` → `files.jsonl`, which is rebuilt from scratch every time. So a deleted `raw/` record drops out of CORPUS's read path at the next rebuild and **cannot reach a CORPUS citation**. What the dangling slug endangers is a link already published in a PDF someone has downloaded — which makes **(a)** a question about `raw/` deletion policy rather than about the index, and makes **(b)** stronger again: the DB is on nobody's read path here.)*

*(**And CORPUS is now out of it entirely, 2026-08-14.** CORPUS builds its own index from `raw/` and `wiki/` and never opens OSINT's. Both halves of this note are OSINT's own call to make on OSINT's own terms — **(a)** is a slug-permanence question the standing constraints already carry, and **(b)** is about a DB only OSINT queries.)*

*(**Stands, and the divergence has widened, 2026-08-16.** `index/` was rebuilt in OSINT this morning — `files.jsonl` and `links.jsonl` are stamped 2026-08-16 11:50/11:51 — and **`vault.db` is still stamped 2026-08-10 06:06**, so the gap the 08-14 annotation measured at three days is now six, and it widened across a full rebuild rather than in spite of one. **5** (2026-08-14) — **Proposal: `INGEST` could establish the earlier position a progress report compares against.** *(Bill's suggestion; recorded here for an OSINT session to weigh, not actioned. Was note 11.)* CORPUS's report ledger carries `position_start` and `position_end` per row — the substance of a position at each end of a twelve-month window, as free text: `30 branches, five banks (2025-08)` against `296 branches, four banks`. `position_end` comes from the record in hand. **`position_start` does not**: establishing it means going back through the wiki for an earlier relevant occurrence of the same object, which is a different kind of search from the one BUILD is doing, and it happens **once per row** — once a row is in the ledger the start position never changes.

That work sits closer to `INGEST` than to CORPUS. INGEST is already reading each new record against the base and is already across places, concepts and intersections, which is exactly the traverse `position_start` needs; CORPUS reaches `raw/` and `index/` read-only and has no equivalent view. Doing it at ingest would also do it at the one moment the question is cheap — while the record is being placed — rather than at report time on a base someone has to re-enter.

Current state, for whatever it is worth to the decision: `position_start` is filled on 4,112 of 5,421 rows (75%), `position_end` on 4,760 (87%). A row with no `position_start` renders ***Baseline not held***, so a quarter of rows currently publish as having no stated baseline. Bill's own view is that the field is ambitious and he is **not confident it is currently accurate** — so this is worth settling on correctness grounds, not only on where the work belongs. Nothing in CORPUS blocks on it; the field degrades gracefully.

*(**Stands, and the figures have not moved, 2026-08-16.** Re-measured over all 57 ledgers: **4,117 of 5,454 rows** carry a `position_start` (75%) and 4,782 a `position_end` (88%). The ledgers grew by 33 rows in two days and the ratio is unchanged, which says the gap is structural rather than a backlog being worked off — new rows arrive without a start position at about the same rate as the held ones. The proposal is still undecided and nothing in CORPUS has come to depend on it.)*

**17** (2026-08-16) — **Proposal: put a mechanical pre-filter in front of `INGEST` tier 3, rather than moving content dedup out of OSINT.** *(Bill's question — could BUILD do the duplicate check instead, and would it be cheaper? Recorded here for an OSINT session to weigh, not actioned, in the same form as note 5. CORPUS investigated the relocation and does not recommend it; the reasoning is below so the question does not have to be re-opened from scratch.)*

The question was whether `INGEST.md` §2's content dedup — are two sources reporting the same issue, is one better, are both useful — could move into CORPUS's BUILD, on the grounds that OSINT runs it on everything regardless of relevance to CORPUS.

**The relevance premise turns out to be nearly empty.** `outputs/catalogue/raw-catalogue.csv` holds 9,407 records and exactly **3** carry no place tag; CORPUS holds 57 ledgers covering every African country plus XAF, XSA and XWA, and 8,745 unique slugs already appear in some unit's `considered.txt`. Where BUILD *is* narrower is on movement rather than subject — most sources report activity, not movement — but BUILD only knows that after reading the source, so the narrowness saves no reading.

**Relocation would raise total cost, not lower it, for three reasons.** BUILD reads per unit and OSINT ingests once: across the 57 `considered.txt` files there are 11,307 unit-considerations over 8,745 unique slugs, a 1.29× multiplier, with 16% of sources read by two to ten units — so one pair adjudicated once in OSINT would come up once per unit in BUILD. A drop in OSINT compounds and a filter in BUILD does not: the verdict is written to `logs/sweep-url_log.md` at the item's disposition, so every future sweep pre-filters that URL before fetching, and BUILD has no equivalent lever and nowhere to write one. **CORPUS gets duplicate-immunity for its reports free anyway.** `sources` on a ledger row is `|`-separated, so two outlets reporting one movement produce one row move carrying both slugs. The ledger is the content dedup, at the point of use. CORPUS's only real exposure to duplicates is the catalogue, where a duplicate is untidy rather than wrong.

**What the cut is probably worth, so the effort goes where the tokens are.** The close line for the 2026-08-12 `update-wiki` call records 197 items ingested against 33 sub-agents — 31 Phase A/B, 1 iteration batch, **1 adjudicator**. Tier 3 has already been cut twice, by token-review task 13 (rule, not judgement) and tasks 22–23 (Opus confined to a declared subagent invoked only once tier 2 has narrowed). What that review named as the large recurring costs were nightly model-lint (task 17) and gap probes (task 15, ~20% of a run). One caveat CORPUS cannot see past: tier-2 narrowing runs inline inside each Phase A slice and is not separately counted, so if dedup feels expensive it is more likely tier 2 across ~200 items than the single Opus call — and tier 2 is the half that is already mechanical.

**The proposal, then, is to mechanise the routine majority rather than relocate the judgement.** CORPUS already runs this exact decision as a script. `scripts/status-pool.py` pools facts from many sources and settles same-thing / better-copy / both-useful with a Jaccard token overlap on the fact text, two thresholds (loose within one source, tight across sources), a confidence-then-tier-then-date sort so the survivor is always the better copy, and a union of slugs plus an `also` list carrying the second URL. A script scoring the tier-2 candidate handful could auto-drop the obvious echoes and pass only genuine ambiguity to the `adjudicator`, keeping the gate where it has to be and keeping the compounding sweep-filter saving. The rule it would implement is the one `INGEST.md` §2 already states, so this is an implementation of existing policy, not a change to it.

**21** (2026-08-17) — **Proposal: commit at each stage boundary of a sweep cycle rather than once at the end of it.** *(Raised from observing a Day 2 cycle in flight. **The pattern is on the record in the previous cycle's own commit message.** `4b16590d` (2026-08-16 22:55) reads *"Sweep cycle Day 1: newspapers/journals/thinktanks + daily/off-list, ingest, compile, lint"* — four stages in one commit at the end of the run. Observed at 11:30 on 2026-08-17, the Day 2 cycle had just moved from ingest to lint with **123 uncommitted entries** in the working tree — 71 untracked and 52 modified — against a `HEAD` last written **more than twelve hours earlier**. So the boundaries between stages already exist and are already named; what is missing is a commit at them.

What was outstanding at that moment, by directory: **60 new records in `raw/2026`** and one in `raw/2025`, **22 rewritten pages under `wiki/places`**, 14 files under `outputs/non-state-finance`, 12 under `sweep/` (daily, off-list, financiers), 9 under `logs/`, 2 under `reviews/` and one in `lookups/`.

**The cost lands on the stage that comes next, because LINT edits files.** Its edits arrive in the same undifferentiated pile as ingest's 61 new records and 22 rewritten place pages, with nothing at `HEAD` to diff either half against. That makes a wrong lint edit expensive to back out in a way it need not be: with a commit at the ingest boundary it is one `git checkout` of one path against a known-good tree, and without one it is a hand-audit of 123 files to work out which of them lint touched at all. The same applies to any later stage against any earlier one.

**And a long cycle's likeliest ending is not a clean one.** The session under observation had been running about thirteen hours. A run that ends by exhausting its context mid-stage leaves a tree that is well-formed, resolves its links and passes its checks, and is silently half-done — nothing in it distinguishes that from a finished cycle. A commit at each boundary converts that from an unreadable state into a legible one: `HEAD` says which stages completed, and the uncommitted remainder is exactly the stage that was interrupted. It also makes the cycle resumable on evidence rather than on recollection.

**This is the standing constraint at the top of this file, applied one level down.** That constraint requires `raw/`, `wiki/` and `lookups/` to stay tracked and committed, on the grounds that a tree which does not commit leaves every change since the last commit at risk together. Committing once per cycle satisfies it in letter while leaving a twelve-hour window in which it is not true in substance. The files are on disk throughout, so nothing is *lost* by the current pattern — what is lost is the ability to say what a run did, and when.

**The change is cheap: the same work, three or four commits instead of one.** No stage has to be reordered and no runbook step has to move; each named stage ends with a commit whose message is the clause that stage already contributes to the single message today. If there is a reason the cycle commits at the end — an atomicity property across stages that a partial commit would break — it should be written down, because from outside it reads as an accident of the runbook's shape rather than a decision.
