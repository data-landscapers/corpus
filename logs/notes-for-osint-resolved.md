**17** (2026-08-16) — *Withdrawn 2026-08-17, before any OSINT session weighed it. Bill's read is that **OSINT's token usage is currently good**, which removes the note's whole premise: every argument in it is about what a change would cost or save in tokens, so with no cost pressure there is nothing for the proposal to buy. It was never a defect report and nothing in CORPUS depends on it. The text is kept in full because the investigation behind it — that relocating content dedup to CORPUS would raise total cost rather than lower it — is the part worth not repeating, and it stays true whatever happens to token budgets.*

**Proposal: put a mechanical pre-filter in front of `INGEST` tier 3, rather than moving content dedup out of OSINT.** *(Bill's question — could BUILD do the duplicate check instead, and would it be cheaper? Recorded here for an OSINT session to weigh, not actioned, in the same form as note 5. CORPUS investigated the relocation and does not recommend it; the reasoning is below so the question does not have to be re-opened from scratch.)*

The question was whether `INGEST.md` §2's content dedup — are two sources reporting the same issue, is one better, are both useful — could move into CORPUS's BUILD, on the grounds that OSINT runs it on everything regardless of relevance to CORPUS.

**The relevance premise turns out to be nearly empty.** `outputs/catalogue/raw-catalogue.csv` holds 9,407 records and exactly **3** carry no place tag; CORPUS holds 57 ledgers covering every African country plus XAF, XSA and XWA, and 8,745 unique slugs already appear in some unit's `considered.txt`. There is no large body of admitted material that CORPUS has no use for. Where BUILD *is* narrower is on movement rather than subject — most sources report activity, not movement — but BUILD only knows that after reading the source, so the narrowness saves no reading.

**Relocation would raise total cost, not lower it, for three reasons.** BUILD reads per unit and OSINT ingests once: across the 57 `considered.txt` files there are 11,307 unit-considerations over 8,745 unique slugs, a 1.29× multiplier, with 16% of sources read by two to ten units — so one pair adjudicated once in OSINT would come up once per unit in BUILD. A drop in OSINT compounds and a filter in BUILD does not: the verdict is written to `logs/sweep-url_log.md` at the item's disposition, so every future sweep pre-filters that URL before fetching, and BUILD has no equivalent lever and nowhere to write one. And with no admission gate the duplicates would sit in `raw/` permanently, reach `raw-catalogue.csv` — the table CORPUS publishes for download — and land on the hubs, which is the failure `hub_line_sources` exists to prevent.

**CORPUS gets duplicate-immunity for its reports free anyway.** `sources` on a ledger row is `|`-separated, so two outlets reporting one movement produce one row move carrying both slugs. The ledger is the content dedup, at the point of use. CORPUS's only real exposure to duplicates is the catalogue, where a duplicate is untidy rather than wrong.

**What the cut is probably worth, so the effort goes where the tokens are.** The close line for the 2026-08-12 `update-wiki` call records 197 items ingested against 33 sub-agents — 31 Phase A/B, 1 iteration batch, **1 adjudicator**. Tier 3 has already been cut twice, by token-review task 13 (rule, not judgement) and tasks 22–23 (Opus confined to a declared subagent invoked only once tier 2 has narrowed). What that review named as the large recurring costs were nightly model-lint (task 17) and gap probes (task 15, ~20% of a run). One caveat CORPUS cannot see past: tier-2 narrowing runs inline inside each Phase A slice and is not separately counted, so if dedup feels expensive it is more likely tier 2 across ~200 items than the single Opus call — and tier 2 is the half that is already mechanical.

**The proposal, then, is to mechanise the routine majority rather than relocate the judgement.** CORPUS already runs this exact decision as a script. `scripts/status-pool.py` pools facts from many sources and settles same-thing / better-copy / both-useful with a Jaccard token overlap on the fact text, two thresholds (loose within one source, tight across sources), a confidence-then-tier-then-date sort so the survivor is always the better copy, and a union of slugs plus an `also` list carrying the second URL. That is the shape of the tier-3 rule at zero model tokens. A script scoring the tier-2 candidate handful could auto-drop the obvious echoes and pass only genuine ambiguity to the `adjudicator`, keeping the gate where it has to be and keeping the compounding sweep-filter saving. The rule it would implement is the one `INGEST.md` §2 already states, so this is an implementation of existing policy, not a change to it.

Worth knowing that the rule is visibly working where it is hard: `2026-08-06-unitel-restores-core-services-after-nationwide-cyberattack` carries an `ingest_note` recording a **keep-both** against its sibling with the payload difference stated in one line, exactly as §2 requires. A pre-filter has to leave that class alone, which is the whole design constraint — it should be tuned to drop confidently and escalate everything else.
